# 「新手小白自建 RAG」系列發布計劃

> 編輯用內部文件,不會被 Hugo 發布。
> 最後更新:2026-08-07

## 系列定位

- **敘事視角**:作者本人就是小白,第一人稱記錄「一步一步搞懂並建立 RAG」的過程。不是教學文,是探索日誌——有疑問、有查證、有踩坑。
- **核心故事線**:中年 CRUD 工程師求職上岸到新公司,發現系統**文件偏少、坑很多**,先用 doobidoo/mcp-memory-service 讓 AI 助手記錄踩坑筆記、在開發者之間同步坑點,嘗到甜頭後把公司文件倒進去想做知識庫,結果錯答連發、惡夢開始。作者痛定思痛從零手刻 RAG 搞懂原理,先拿自己的踩坑筆記練功,再回頭馴服公司知識庫,最終挑戰「把口述傳承變成問了就答的知識庫」。
- **目標讀者**:會寫一點程式、用過 ChatGPT,但沒碰過 RAG 的人;用過 mcp-memory-service 這類現成工具但不懂原理的人;以及面臨「文件少、知識都在老同事腦裡」困境的上班族工程師。
- **差異化**:(1) 小白第一人稱的真實踩坑紀錄;(2) 從現成工具(mcp-memory-service)的失敗經驗出發、回頭補原理再回來解剖工具的敘事;(3) 第二部「跟人互動、萃取口述知識」是市面 RAG 教學幾乎沒有的內容。

### 第 2 篇大綱（定稿，2026-08-07)

**標題（暫定）**：我以為把文件丟進去就好了|**型態**：故事+技術

1. **開場（接第一篇結尾）**：第一版知識庫誕生，規格很樸素——mcp-memory-service 當儲存體，Slack 收到訊息觸發搜尋，把撈到的相關筆記貼回頻道（bot 為作者自寫）；離「AI 直接給答案」還很遠，先讓「找得到資料」能動。附 mermaid 架構圖。短暫的美好時光
2. **惡夢一：搜尋不到**：明明存過，換個問法就撈不到。現象用對話呈現；排查：提問用詞與寫入敘述的語意距離、中文 embedding、筆記寫太長；緩解：問題導向敘述、補 tags
3. **惡夢二：寫入時的語意衝突（A is B 問題）**：相互矛盾的記憶並存，撈到哪個看運氣；緩解：search-before-store、更新取代新增、日期/版本標記
4. **惡夢三：Top-k 漏資訊**：關鍵資訊排在第 k+1 筆被切掉；自然帶出「檢索是撈最相近 k 筆」的原理；trade-off:k 大雜訊淹沒重點、k 小漏答
5. **小結+伏筆**：搜尋堪用了，但 AI 統整回答還沒上場（伏筆方向待定）

## 排版與風格偏好（review 檢查用）

> 整理自第一篇逐段編輯的回饋，之後有新偏好持續補充。

- **標點**：中文內文一律全形；程式碼、URL、Markdown/TOML 語法保持半形
- **對話呈現**：互動情境優先寫成對話，不用條列；用引用區塊，格式「**角色**：台詞」，說話者一律粗體；句與句之間以 `>` 空行分隔
- **對話框間距**：對話框與內文之間，前後各插一行 `<br>` 加大間隔
- **段落分隔**：每個段落（`##` 標題區塊）結尾加 `---` 分隔線
- **場景/時間轉換**：用 `<br>` 停頓，可搭配 emoji 標記（例：`<br> 📅` + 「一個禮拜過去……」）
- **Punchline 獨立呈現**：冷面笑點用 code block 自成一行（例：`mcp called count: 3`），後面可補一句反差註解
- **名詞解釋不打斷正文**：較長的背景說明（如 MCP 是什麼）移到文末「附錄」，正文維持敘事節奏
- **語氣**：第一人稱自嘲+遊戲/網路梗（冒險的 Start 按鍵、C 牌奴隸、前輩三連喔喔喔）
- **刪贅句**：讀者已知的名詞不展開解釋（如 CRUD）；疊詞擇一（「紛紛都」→「紛紛」）
- **錯字與慣用語**：提交前檢查誤植（「來到到」）與慣用語（「平靜海面下的暗流」，非「波面」）
- **故事篇不塞技術**：故事篇負責動機與劇情，技術解釋留給技術篇；不把故事寫成 AI 教科書
- **概念伏筆先埋**：跨篇的關鍵轉折（如「知識庫 → 直接問 AI → RAG」）要在前一篇埋好一句伏筆，下一篇才接得自然；仍不放明示的下集預告
- **結尾節奏**：「天真宣言 → 至少，當時的我是這麼想的。 → 惡夢伏筆」三連拍；短句獨立成段製造停頓
- **口語吐槽感**：避免過度文雅的修飾詞，選字往口語靠（「詭譎」→「詭異」）
- **對話不改說明文**：對話場景保留原汁對白，不改寫成間接敘述，那會失去人格
- **不宣揚理念**：避免說教與理念宣言式的句子（「我要做的不是 X，而是 Y」這類），想法讓劇情和對話自己講
- **AI 輔助聲明**：每篇文末固定加註「*本文由 AI 輔助潤稿*」
