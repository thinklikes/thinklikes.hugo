## 系列定位

- **敘事主軸**:第一人稱記錄**作者在公司內從零建立各種 AI 應用**的過程。不是教學文,是探索日誌——有疑問、有查證、有踩坑。RAG 知識庫是第一個應用,不是全部;主題會隨 side project 實際做到哪裡往外長。
- **核心故事線**:中年 CRUD 工程師求職上岸到新公司,發現系統**文件偏少、坑很多**,於是動手把 AI 帶進公司——先用 doobidoo/mcp-memory-service 讓 AI 助手記錄踩坑筆記、在開發者之間同步坑點,嘗到甜頭後想做客服知識庫,結果惡夢連發。痛定思痛從零手刻 RAG 搞懂原理,先拿自己的踩坑筆記練功,再回頭馴服公司知識庫,挑戰「把口述傳承變成問了就答的知識庫」;之後繼續往外擴,做公司裡的下一個、再下一個 AI 應用。
- **目標讀者**:會寫一點程式、用過 ChatGPT,但還沒真正把 AI 帶進公司的人;用過現成 AI 工具但不懂原理的人;以及面臨「文件少、知識都在老同事腦裡」困境的上班族工程師。
- **差異化**:(1) 小白第一人稱的真實踩坑紀錄;(2) 從現成工具(mcp-memory-service)的失敗經驗出發、回頭補原理再回來解剖工具的敘事;(3)「跟人互動、萃取口述知識」是市面 RAG 教學幾乎沒有的內容;(4) 主題不侷限 RAG——記錄的是「在一間文件稀缺的公司裡,一個人怎麼把 AI 應用一個個長出來」。

> **關於系列命名**:目前已發布文章的 `topics` 仍為 `新手小白自建 RAG`(第一個 AI 應用的故事線)。若要把 topic 改成更大的傘狀名稱,會動到已發布文章的 taxonomy 網址,需作者決定後再一起改。

## 寫作與發布流程

1. **討論大綱**:作者與 Claude 就主題討論出該篇大綱
2. **作者執筆**:作者依大綱自行撰寫內容(`draft = true`,開發於 feature branch)
3. **交叉 review**:找 Claude review、也找 ChatGPT review,作者定稿
4. **上稿發布**:`draft = false` 後開 PR;**PR 一律由作者確認後才合併,不自動合併**。merge 進 master 即自動發布(Cloudflare Pages 自動建置,build command `hugo --gc --minify`,`HUGO_VERSION=0.145.0`)

### 第 2 篇大綱（v3 定稿，2026-08-07)

**標題**:沒有珍珠的奶茶不是珍珠奶茶，沒有資料的知識庫不是知識庫（定案）|**型態**：故事（純現象與踩坑，不解釋原理）

**結構**：不用暖身橋段（原「週五幻想／週一開工」開場已捨棄），直接以惡夢一開場。文章內不標「惡夢一二三四」，各節用白話小標；「四大惡夢」只是內部用語。

1. **開場＝惡夢一：我有知識庫，你有資料嗎？**（哏取自「我有酒，你有故事嗎？」）——一句話帶過架構（mcp-memory-service + 自寫 Slack bot，搜尋後原封不動回貼，尚未接 AI）+ mermaid 圖；塞兩筆測試資料測試成功的短暫得意（順帶一句「年底考績會很好看」，即壓縮版加薪哏，留到文末回收）；打開知識庫發現裡面就只有那兩筆 → **所以我現在要放什麼進去？** 公司文件要嘛沒有要嘛太舊、前輩在忙；**因為不知道該放什麼，索性看到什麼就狂塞**——會議記錄、Slack 對話、隨手筆記、舊文件，先求有。此節點到為止（只寫當下的病急亂投醫），系統性的知識盤點方法論留給第 8 篇
   - ↑ **狂塞是後面三個惡夢的病根**：內文太長導致語意稀釋、同句式重複導致寫入被拒、資料一多 top-k 就撈不完。四個惡夢因此有因果關係，不只是並列
2. **明明存過，怎麼就是搜不到？**——換個問法就撈不到；排查：單筆知識內文太長（整份會議記錄貼成一筆），語意被稀釋；緩解：拆成單一事實（一筆記憶只講一件事）
3. **這筆知識，系統說它已經有了**——「A 是 B」句式太相似，被重複判斷當成同一筆，**新知識寫入被拒絕**；嘗試一：更換嵌入模型（all-MiniLM → bge-m3），改善但沒根治；最終：降低重複判斷門檻
4. **答案在第六筆**——關鍵內容排在第 k+1 筆被切掉；把 5 調到 10 過關，但沒真的解決
5. **小結+伏筆**——搜尋總算堪用（三招都是繞過去的，沒一招真的解決），「考績／加薪」哏回收；結尾伏筆方向待定

> 每節統一模板：現象 → 內心 OS 吐槽 → 排查 → 土法緩解 → 一句話學到一課。**全篇不解釋原理**，只寫現象與當時的補救；原理留給後續技術篇。

## 排版與風格偏好（review 檢查用）

> 整理自第一篇逐段編輯的回饋，之後有新偏好持續補充。

- **標點**：中文內文一律全形；程式碼、URL、Markdown/TOML 語法保持半形
- **對話呈現**：互動情境優先寫成對話，不用條列；用引用區塊，格式「**角色**：台詞」，說話者一律粗體；句與句之間以 `>` 空行分隔
- **對話框間距**：對話框與內文之間，前後各插一行 `<br>` 加大間隔
- **段落分隔**：每個段落（`##` 標題區塊）結尾加 `---` 分隔線
- **場景/時間轉換**：用 `<br>` 停頓，可搭配 emoji 標記（例：`<br> 📅` + 「一個禮拜過去……」）
- **Punchline 獨立呈現**：冷面笑點用 code block 自成一行（例：`mcp called count: 3`），後面可補一句反差註解
- **名詞解釋不打斷正文**：較長的背景說明（如 MCP 是什麼）移到文末「附錄」，正文維持敘事節奏
- **語氣**：第一人稱自嘲+遊戲/網路梗（冒險的 Start 按鍵、C 牌奴隸、前輩三連喔喔喔）
- **刪贅句**：讀者已知的名詞不展開解釋（如 CRUD）；疊詞擇一（「紛紛都」→「紛紛」）
- **錯字與慣用語**：提交前檢查誤植（「來到到」）與慣用語（「平靜海面下的暗流」，非「波面」）
- **故事篇不塞技術**：故事篇負責動機與劇情，技術解釋留給技術篇；不把故事寫成 AI 教科書
- **概念伏筆先埋**：跨篇的關鍵轉折（如「知識庫 → 直接問 AI → RAG」）要在前一篇埋好一句伏筆，下一篇才接得自然；仍不放明示的下集預告
- **結尾節奏**：「天真宣言 → 至少，當時的我是這麼想的。 → 惡夢伏筆」三連拍；短句獨立成段製造停頓
- **口語吐槽感**：避免過度文雅的修飾詞，選字往口語靠（「詭譎」→「詭異」）
- **對話不改說明文**：對話場景保留原汁對白，不改寫成間接敘述，那會失去人格
- **不宣揚理念**：避免說教與理念宣言式的句子（「我要做的不是 X，而是 Y」這類），想法讓劇情和對話自己講
- **AI 輔助聲明**：每篇文末固定加註「*本文由 AI 輔助潤稿*」
