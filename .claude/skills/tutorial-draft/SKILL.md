# 教學文草稿

給不懂技術的讀者看的操作教學，例如「註冊 GitHub 並開啟兩步驟驗證」「ChatGPT 畫好的貼圖怎麼上架到 LINE」。讀者通常是在 LINE 群組裡被貼連結過來的，看完要能自己照著做完。

範例文章（動筆前先讀一遍）：

- `content/posts/ai-tools/line-sticker-upload/index.md`
- `content/posts/ai-tools/github-signup-2fa/index.md`

本 skill 只管教學文。RAG 系列（`中年碼農的 AI 職場冒險記`）的故事體寫法另見 `docs/rag-series-plan.md`，不要套用在這裡。

---

## 一、先做題目評估（抗性思辨）

動筆前，先用反方的角度挑戰題目，把結論寫給作者看，作者同意才開始寫。

好的教學題目要同時符合：

1. 讀者會卡在這裡，而且不只一個人、不只一次
2. 用文字回答講不清楚，需要截圖，所以貼連結比打字快
3. 不容易過時，介面改了也只要換截圖
4. 不在別人付費課程的範圍內（避開清單見 `/mnt/project-files/ideas/blog-ideas-from-line-groups.md`，若可讀取）

每個題目至少回答以下反方問題，各寫一兩句：

- **太簡單，不值得一篇？** 對工程師簡單不代表對讀者簡單；短篇也可以。
- **網路上已經有人寫了？** 這篇的價值是什麼：較新的截圖、只寫和 AI 有關的情境、能讓其他文章連過來。
- **介面一改就過時？** 哪些步驟不會變、哪些只要換截圖。
- **範圍會不會寫不完？** 例如 Windows、Mac、手機要不要都寫；明確寫出不寫什麼。
- **證據是什麼？** 群組裡有人問過，還是推論。推論要標「推論」。

結論分成「保留」「候補」「刷掉」，並給排序。

## 二、查證：不要憑記憶寫介面

- 流程、按鈕名稱、選單路徑、數量（例如救援碼幾組）、規格（尺寸、檔案大小）一律查官方文件或官方說明頁，寫作當天查。
- 介面是英文時，按鈕名稱保留英文原文並用粗體，例如 **Settings**、**Enable two-factor authentication**，前後用中文說明。
- 官方文件沒有寫清楚的部分（例如註冊頁每一欄），寫得概括一點，並在 PR 說明裡註明「截圖時請對照實際畫面調整」，不要自己補細節。
- 官方文件列在文末「參考資料」。

## 三、文章結構

檔案放在 `content/posts/<系列資料夾>/<slug>/index.md`（page bundle），圖片和 `index.md` 放同一層。

Front matter：

```toml
+++
date = 'YYYY-MM-DD'
draft = true
title = '<系列名>（N） - <讀者要解決的問題>'
description = '<80 字內，講讀者看完能做到什麼>'
tags = ['<工具名>', '<主題>']
topics = ['<系列名>']
+++
```

- 系列名與編號：沿用現有系列（目前有 `AI 省時小工具`）。題目不屬於任何系列，或作者另開「基礎教學」系列時，先問作者，不要自己決定。
- 一律 `draft = true`，作者定稿後才改。

段落順序（每個 `##` 區塊結尾加 `---`）：

1. **前言**：一兩段，講這篇要解決什麼、大約要花多少時間。作者自己的動機或經驗留 `【作者補：…】`，不要代寫。
2. **動手前**：要準備的東西（帳號、手機、電腦）用條列；規格類資訊用表格。
3. **步驟一、步驟二……**：每個步驟一個 `##`，標題寫動作（「步驟三：在 GitHub 開啟兩步驟驗證」）。
   - 操作用編號清單，一行一個動作。
   - 要複製貼上的提示詞用 ` ```text ` code block，可替換的地方用【】標出。
   - 「結果不理想時怎麼辦」用兩欄表格：狀況 ｜ 複製這句貼給 ChatGPT。
   - 步驟段落裡不寫踩坑故事，只寫該怎麼做。
4. **完成之後**：審核結果、之後登入會看到什麼、如何補救。作者的使用心得留 `【作者補】`。
5. **參考資料**：`###` 標題，官方文件與概念來源（參考別人的開源專案時，只引用概念並致謝，不把讀者導去用那個工具）。
6. 文末固定一行 `*本文由 AI 輔助潤稿*`。

## 四、截圖預留位置

作者會自己截圖上傳，文章裡先放好固定檔名的圖片連結，下一行用 HTML 註解寫明要截的畫面：

```markdown
![github-2fa-qrcode.png](github-2fa-qrcode.png "掃描 QR code")
<!-- 截圖：GitHub 顯示 QR code 與「Verify the code from the app」輸入欄位的頁面（QR code 請打馬賽克） -->
```

規則：

- 檔名用英文小寫加連字號，前綴是工具名（`github-`、`line-`、`chatgpt-`），一看就知道是哪個畫面。
- 檔名不能含 `feature`、`cover`、`thumbnail`（包括 `recovery` 這種內含 cover 的字），Congo 主題會把這種檔名的圖當成封面圖。
- 圖片的 title（引號內）寫成讀者看得懂的中文說明，會顯示成圖說。
- 註解要具體到「哪一頁、要標出哪個按鈕」。
- 畫面裡有 QR code、驗證碼、救援碼、Email、電話、訂單等個資時，在註解裡提醒打馬賽克。
- 圖放在對應步驟的操作清單之後；一個步驟最多兩三張，不要每一行都配圖。

## 五、語氣與用字

- 第一人稱，口語但中性，句子完整；不要速記式的短句。
- 不用主觀或情緒化的字眼（例如「龜毛」「最醜」「兇它」），改成中性說法，例如「建議使用電腦操作較為順暢」。
- 避開 AI 腔：泛用開場（「很多人第一次……都會卡在同一件事」）、承諾清單、「其實……原理是這樣」、空洞總結、誇大效果。
- 名詞第一次出現附中文與原文，例如「兩步驟驗證（Two-factor authentication，簡稱 2FA）」。讀者已經知道的名詞不展開。
- 中文內文標點一律全形；程式碼、URL、Markdown／TOML 語法保持半形。
- `{{< alert >}}` 只用在真正要警告的地方（安全、帳號會拿不回來、肖像權），一篇兩三個以內；粗體也少用。
- 不放系列規劃，不寫「下一篇會教……」。

## 六、交付

1. 在 feature branch 上 commit，更新 `CLAUDE.md` 的「目前進度」。
2. 開 PR（不自動合併），PR 說明包含：
   - 文章重點與查證日期、參考的官方文件
   - 文中所有 `【作者補】` 的位置
   - **要上傳的截圖清單**：放置路徑（`content/posts/<系列資料夾>/<slug>/`）＋ 表格（檔名 ｜ 要截的畫面），和文中註解一致
   - 需要作者判斷的事（系列歸屬、官方文件沒寫清楚的步驟）
3. 交付前自我檢查：
   - [ ] 題目評估已給作者看過
   - [ ] 每個按鈕名稱、數字都查過官方文件
   - [ ] 每張圖都有固定檔名、圖說與截圖註解，PR 清單與文中一致
   - [ ] 個資畫面都有打馬賽克提醒
   - [ ] 標點全形、沒有 AI 腔開場與空洞總結
   - [ ] `draft = true`，文末有「本文由 AI 輔助潤稿」
