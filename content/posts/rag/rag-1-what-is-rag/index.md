## 前言:我為什麼要自找麻煩

事情是這樣的。我把自己累積多年的筆記丟給 ChatGPT,問它一個我明明記過的問題,結果它一臉誠懇地掰了一個不存在的答案。那一刻我突然意識到:**AI 再聰明,它也沒讀過我的資料**。

而且我還有一個更大的野心。我們公司是那種**長期依賴人工處理與口述傳承**的地方:報價要問資深的 A、出貨流程只有 B 全懂、某台機器的眉角只存在 C 的腦子裡。文件?有,但零散、過時、沒人敢保證是最新版。每次有老同事離職,就有一塊知識跟著蒸發。我一直在想:如果能把這些東西一步步整理起來、匯入一個問了就答的系統,那該有多好。

查了一下,這個問題的解法叫 `RAG`(Retrieval-Augmented Generation,檢索增強生成)。網路上的文章要嘛是名詞解釋,要嘛一開頭就丟一堆框架程式碼,對我這種小白很不友善。於是我決定:**自己從零開始建一個 RAG,把過程原原本本記錄下來**——包含我搞懂了什麼、卡在哪裡、踩了什麼坑。先拿自己的筆記練功,練成之後,再去挑戰公司那座口述傳承的大山。

先報一下我的等級,讓你知道這個系列的起點有多低:

- 會寫程式,但 Python 只有「照著範例改」的程度
- 機器學習?零。線性代數還給老師了
- LLM 使用經驗 = 會跟 ChatGPT 聊天

如果你跟我差不多,那我們的起跑線是同一條。

## 第一步:RAG 到底是怎麼運作的?

動手之前,我逼自己先搞懂原理——不然照抄程式碼跑起來了,壞掉也不知道從哪修。以下是我消化各種資料後,總算讓自己聽懂的版本。

### 我的理解:讓 AI 從閉書考試變成開書考試

想像 LLM 是一位很會考試的勇者:

- **直接問 LLM** = 閉書考試。勇者只能靠訓練時背下來的知識作答。考古題(公開網路資料)它很強,但我的私人筆記它沒背過,只好瞎掰——這就是所謂的**幻覺(hallucination)**,也就是我開頭遇到的慘案。
- **RAG** = 開書考試。考試前,先把我的筆記整理好放在勇者手邊;答題時,勇者先翻到相關段落,再根據段落內容作答。

所以 RAG 根本不是重新訓練模型(我原本以為要,嚇得半死),而是**在提問的當下,把相關資料塞給模型參考**。模型完全不用動,變的只是它拿到的參考資料。

{{< alert "circle-info" >}}
我一開始的疑問:那幹嘛不直接把整份筆記貼進對話視窗就好?

查完發現小文件確實可以!但文件一多就撞牆:上下文長度有限、塞太多雜訊模型反而抓錯重點、每次都塞全部又慢又花錢。RAG 的核心價值就是「**只挑相關的段落**給模型」。搞懂這點之後,後面的流程就都說得通了。
{{< /alert >}}

### 把流程攤開來看

我把查到的資料整理成一張圖。整個系統分成兩條路線:**建立知識庫**(事前做一次)與**問答**(每次提問都會發生):

    subgraph 建立知識庫["事前準備:建立知識庫"]
        A[我的筆記<br>PDF/Markdown/網頁] --> B[切塊 Chunking]
        B --> C[嵌入 Embedding<br>文字轉成向量]
        C --> D[(向量資料庫)]
    end
    subgraph 問答["每次提問"]
        Q[我的問題] --> E[問題也做嵌入]
        E --> F[到向量資料庫<br>檢索相似段落]
        D --> F
        F --> G[相關段落 + 問題<br>組成 Prompt]
        G --> H[LLM 生成回答]
    end
{{< /mermaid >}}

五個步驟,我逐個用自己的話翻譯一遍:

1. **切塊(Chunking)**:把長文件切成一段一段的小塊。就像把整本秘笈拆成一張張小抄,之後才好精準地翻找。
2. **嵌入(Embedding)**:用「嵌入模型」把每個文字塊轉成一串數字(向量)。神奇的是,**意思相近的文字,轉出來的數字也會相近**——這是整個 RAG 最魔法的地方,我目前先接受它是魔法,之後打算專門開一篇實驗給自己看。
3. **向量資料庫(Vector Database)**:專門存放向量、而且能快速回答「哪些向量跟這個查詢最像」的資料庫。
4. **檢索(Retrieval)**:把我的問題也轉成向量,到資料庫裡撈出最相近的幾個文字塊。
5. **生成(Generation)**:把撈到的文字塊和我的問題組成一個 Prompt,交給 LLM 產生最終回答。

寫到這裡我自己順了一遍:**原來 RAG 就是「先用向量找資料,再讓 LLM 看著資料回答」**,前面四步都是在做一件事——讓第五步的勇者拿到對的小抄。

{{< alert "triangle-exclamation" >}}
查資料時看到的警告,先記下來提醒未來的自己:RAG 不是銀彈。如果檢索撈不到對的段落,LLM 拿著錯的小抄,照樣會答錯。所以「怎麼知道我的 RAG 準不準」之後一定要面對,不能建完就當它會動。
{{< /alert >}}

## 順便決定:我要用什麼工具

原理懂了,接著我花了一個晚上研究要用什麼工具。身為小白兼小氣鬼,我的篩選條件是:**免費、能在自己筆電上跑、資料不外流、程式碼越少越好**。最後清單長這樣:

| 裝備 | 我的選擇 | 為什麼選它 |
|------|------|--------|
| 程式語言 | Python | 範例最多,卡關時最好找答案 |
| LLM 與嵌入模型 | [Ollama](https://ollama.com/) | 一行指令就能在本機跑模型,免費,筆記不用上傳到任何地方 |
| 向量資料庫 | [Chroma](https://www.trychroma.com/) | `pip install` 就能用,不用架伺服器 |
| 框架 | 先不用 | LangChain 很紅,但我怕框架把細節包起來,我學完還是不懂原理。先手刻,懂了再說 |

{{< alert "lightbulb" >}}
查證過:沒有獨立顯卡也能玩,選小一點的模型,一般筆電 CPU 跑得動,只是回答速度慢一些。這對我這台老筆電是個好消息。
{{< /alert >}}

## 小結

第一步完成:我總算搞懂 RAG 是怎麼運作的了——**與其讓 LLM 閉書瞎掰,不如把我的筆記切塊、轉成向量存起來,提問時撈出相關段落,讓它開書作答**。

原理懂了,工具也選好了,接下來就是動手。至於練功的過程會多順利(或多慘烈),就讓紀錄自己說話吧。
